Executive Summary

The highest-risk cluster sits where the repo accepts user-controlled input and turns it into executable or generated artifacts. That includes skill frontmatter parsing, dynamic skill loading, MCP wrapper generation, MCP server configuration, and shell hook generation. Those paths are small, but they sit directly on the trust boundary between repository data and code execution.

A second cluster is operational. The code-analysis command crawls recursively without pruning generated directories, module validation counts every file under a module tree, and the repo does not yet have a CI workflow in .github/workflows/ even though package.json already defines the local quality gates. That combination makes it easy for a slow or noisy path to escape detection until a user hits it.

The report also found a few boundary and contract problems that are less dramatic but still important: the show --filter path only matches basenames, the version resolver still has a single-version limit, and malformed MCP config files are quietly treated as empty. Those issues do not all break the CLI immediately, but they do create misleading or stale behavior that will slow down support and erode trust.

What matters most:

Fix the execution boundary first, then the recursive scan and hook machinery, then the versioning and diagnostics gaps. If we remove the places where user input becomes file content or process execution, the remaining issues become much easier to validate and much less risky to ship.

Issue 01 Core P1

Skill frontmatter parsing rejects CRLF files

Title
Skill frontmatter parsing rejects CRLF files.
Kind
Core
Priority
P1
Severity
High
Likelihood
Likely
Impacted area
Skill discovery, skill validation, and skill execution on Windows or on any machine that normalizes files to CRLF.
Failure mode

parseSkill() expects frontmatter delimiters to use literal LF line endings. A skill file written with CRLF never matches the regex, so the skill disappears from discovery and injection flows even though the file is otherwise valid.

Evidence or rationale
  • cli/src/utils/skill-system.ts:65-73 uses /^---\n([\s\S]*?)\n---\n([\s\S]*)$/ and therefore only accepts LF-delimited frontmatter.
  • A direct reproduction returned false for the same frontmatter shape when the input used CRLF line endings.
  • discoverSkills() and the skill commands depend on that parser, so the failure propagates to every skill workflow.
Why this matters

Line endings are not a niche edge case. They are common on Windows, they can appear after editor conversions, and they can arrive from git checkouts. If the parser rejects them, an otherwise valid skill becomes invisible, which creates a support problem that is hard to diagnose from the CLI output alone.

Recommended mitigation

Normalize the frontmatter parse to accept \r?\n, keep the body content unchanged, and preserve the current error path for truly malformed files. Do not rewrite skill files automatically unless the user explicitly asks for that normalization.

Implementation prompt

Work in the current project and resolve the repository root yourself. Inspect cli/src/utils/skill-system.ts and the skill command tests first, then update the parser so a skill frontmatter block survives LF and CRLF input without changing the surrounding body text. Keep the existing success shape for valid files, keep the current failure mode for malformed frontmatter, and avoid any broader refactor of the skill discovery flow. If a line-ending conversion is needed, do it only in memory for parsing, not by rewriting the file on disk. Add targeted tests for LF, CRLF, and malformed frontmatter, then run the repository's skill test command and the new unit test file. Finish by reporting the changed files, the exact tests you ran, the observed results, and any remaining assumptions.

Regression tests
  • Unit: add a temp skill fixture with CRLF frontmatter and assert parseSkill() returns the correct metadata and body, not an error.
  • Integration: create a temp skill repo with CRLF content and verify skill list and skill show still discover the skill.
Additional baseline tests
  • Confirm LF skills still parse exactly as before, including the content string returned to skill inject.
  • Keep the malformed-frontmatter failure path intact so truly broken skill files still surface a useful error.
Acceptance criteria
  • LF and CRLF skill files load identically.
  • Malformed frontmatter still fails with the same user-facing diagnostic path.
  • No unrelated skill CLI output changes, and no file rewriting occurs as part of parsing.
Confidence
High. The parser regex and the CRLF reproduction both point to the same failure mode.
Issue 02 Core P2

Skill cache ignores request-specific loading options

Title
Skill cache ignores request-specific loading options.
Kind
Core
Priority
P2
Severity
High
Likelihood
Possible
Impacted area
Skill loading, dependency resolution, and token budgeting for injections or batch loads.
Failure mode

loadSkillDynamic() caches by skillId alone. If one caller loads a skill with dependencies enabled and a later caller asks for dependencies disabled, the second caller can still receive the first caller's expanded tree from cache.

Evidence or rationale
  • cli/src/utils/skill-system.ts:342-391 defines skillCache and returns skillCache.get(skillId) before it examines resolveDependencies or maxTokens.
  • The cache key does not include any request option, so two calls with different loading intent can reuse the same object.
  • That is especially risky for skill inject and skill load, where token budgets and dependency breadth are user-visible behavior.
Why this matters

The cache is an optimization, not a source of truth. If it ignores the request contract, the CLI can appear to succeed while silently returning the wrong dependency set or the wrong token footprint. That turns a tuning knob into a hidden state leak.

Recommended mitigation

Include the request options in the cache key, or split the cache by loading mode so dependency-expanded and dependency-free loads cannot collide. Keep the public return shape stable, and preserve cache hits for identical option sets.

Implementation prompt

Inspect cli/src/utils/skill-system.ts and the skill command tests first. Update the cache strategy so resolveDependencies and maxTokens cannot be ignored by a previous cached load. Avoid a broad refactor of skill discovery, and do not change the return shape of LoadedSkill. Add tests that load the same skill twice with different options and verify the dependency list and token budget behavior differ as requested. Run the relevant skill unit tests and the existing skill command tests, then report the changed files, command outputs, and any remaining risk around cache invalidation.

Regression tests
  • Unit: load one skill once with dependencies enabled and once with resolveDependencies: false; assert the second result has no inherited dependency tree.
  • Unit: load the same skill under two different maxTokens values and confirm the smaller budget still rejects oversized dependency sets.
Additional baseline tests
  • Keep the current cache hit path for identical option sets.
  • Preserve the current warning behavior for missing dependencies and the current flattening behavior in getSkillContentForInjection().
Acceptance criteria
  • Cache reuse never changes the requested dependency breadth.
  • Budget enforcement still fails when the loaded tree is too large.
  • Identical option sets still benefit from cache hits.
Confidence
High. The cache key and the option checks are both visible in the source.
